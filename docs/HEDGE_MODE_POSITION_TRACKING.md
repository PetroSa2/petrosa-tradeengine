# Hedge Mode Position Tracking

## Data pillar

Positions are persisted through data-manager into MongoDB (operational);
data-manager keeps a MySQL historic copy for analytics. MongoDB is the
operational store: every live-path read and write goes to MongoDB. MySQL holds
a historic reference copy only (statistical analysis, backtesting, research)
and is never read on the live path.

## Overview

The trading engine supports Binance Futures hedge mode, allowing simultaneous
LONG and SHORT positions on one symbol. Position IDs are generated by the
dispatcher, and the position manager sends lifecycle changes through the
data-manager API.

## Position tracking flow

```text
Signal → Dispatcher → Order → Binance execution
                                  ↓
                         data-manager API
                                  ↓
                         MongoDB operational record
                                  ↓
                   MySQL historic copy for analytics
```

The data-manager API is the only persistence boundary used by this service.
Metrics are exported after position open and close events.

## Components

- `tradeengine/dispatcher.py` generates position IDs and submits orders.
- `tradeengine/position_manager.py` manages lifecycle and risk state.
- `tradeengine/metrics.py` exports position and PnL metrics.
- `tradeengine/services/data_manager_client.py` handles persistence requests.

## Position data

The operational position document contains the position ID, strategy, exchange,
symbol, side, prices, quantity, timestamps, status, order IDs, fees, PnL, and
close reason. MongoDB indexes support symbol, strategy, status, and time-based
queries.

## Setup and verification

No database client is configured in the trading engine. Configure the
data-manager endpoint and the service credentials through the deployment
configuration, then verify the data-manager health endpoint before deployment.

Enable and verify Binance hedge mode with the repository's verification script:

```bash
python scripts/verify_hedge_mode.py
```

Deploy with the normal service pipeline and inspect the data-manager and
tradeengine logs if position records are not created.

## Querying and analytics

Operational position reads go through data-manager and MongoDB. Historical
analytics and backtesting may use the MySQL reference copy through
data-manager; those queries must never be placed on a live decision path.

## Troubleshooting

- Confirm the data-manager health check and endpoint configuration.
- Check `create_position_record()` logs and the order's `position_id`.
- Confirm MongoDB availability through data-manager diagnostics.
- Confirm hedge mode and `positionSide` values on Binance.
- Check metrics at the service metrics endpoint and in Grafana.
